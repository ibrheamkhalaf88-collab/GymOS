### مصدر الحقيقة الوحيد: الـComposer — وأين يتكرر

- **النسخة الأم:** `accountStatusOf` في `supabase/functions/gymos-api/index.ts:134-203` مع مساعديها `parseWhen` (93)، `metaTier` (108)، `activationSourceOf` (118)، `LIFETIME_MIN_MS` (104)، `pickPrimaryCode` (207). كل نقاط العرض تمرّ عبرها: قائمة المستخدمين (1660)، التفاصيل (1694)، `runUserOp` قبل/بعد (648/735)، التفعيل (832-833/921-922)، الأكواد (351)، تقرير الانتهاء (1999).
- **النسخة المكرّرة:** `supabase/functions/gymos-expiry-cron/index.ts:88-158` — نسخة حرفية شبه كاملة (نفس المساعدين، سطور 44-158) مع وسم صريح **"KEEP IN SYNC with the API composer"** (سطر 42) والسبب معلن: «Edge Functions deploy independently» (39-41).
- **نسخة جزئية ثالثة:** `gymos-drive-backup/index.ts:49-63` يعيد كتابة منطق `expiryMs()` داخل `codeState()` (نفس معادلة `used_at + days*86400000`، سطر 57) دون الوسم.
- **على العميل:** `js/access.js:31-100` (`computeAccess`) — تكرار **مقصود وموثّق** كحارس UX وليس أمنياً (تعليق SCOPE/HONESTY سطر 9-16).

### تقييم خطر تكرار الـComposer: **4 / 5**

**التبرير:**
1. **الأثر حقيقي ومجرَّب تاريخياً:** انحراف الـcomposer تسبّب سابقاً مشاكل §10.4/§10.5 الموثّقة (trial=0، lifetime معروض monthly) — `docs/CONTRACT-activation-v1445.md` §2 جاء أساساً لإصلاح الانجراف بين المصادر.
2. **حارس الاختبار غير كافٍ:** `tests/expiry-2fa.test.mjs:321` يتحقق فقط من **وجود** `function accountStatusOf(` بالكرون و**وجود** نص التعليق (322: `/KEEP IN SYNC with the API composer/`) — **لا يوجد أي اختبار تطابق سلوكي** بين النسختين. تعديل سطر واحد في API دون الكرون يمرّ CI أخضر.
3. **الأثر عند الانجراف خفي وصامت:** النتيجة = إيميلات تذكير لعملاء خاطئين أو إغفال عملاء مستحقين (dedup على `sub_end` محسوب) — لن يظهر أي خطأ، فقط إيميل مزعج/ناقص لعميل دافع.
4. ما منع النتيجة 5/5: عدد النسختين ثابت (2) والاستخدام أحادي الغرض (إيميلات انتهاء)، والتزامن بين التعديلين وارد لأن كليهما بنفس الريبو ونفس المطورين. الحل الرخيص: اختبار تطابق (استخراج الدوالتين و`node:assert` مقارنة نصية طبيعية، أو استخراجها لملف مشترك `shared/status-composer.ts`).

## 2) قابلية التطوير — قرارات جاهزة مقابل ناقصة / Extensibility: Ready vs Missing

### أ) أدمن ثانٍ / RBAC
| | |
|---|---|
| **الموجود اليوم** | بوابة الأدمن = مقارنة نصية ثابتة `safeEqual(email, ADMIN_EMAIL)` + `safeEqual(password, ADMIN_PASSWORD)` → JWT `admin:true` لمدة 12 ساعة (`gymos-api/index.ts:1094-1151`). `authAdmin(req)` يقرأ فقط عَلَم `admin===true` من التوكن (529-532). جدول `admin_2fa` مفهرس بـ`admin_email` **أحادي** (`0012_admin_2fa_contact_resolved.sql:26-32`)، وكل نقاط 2FA تكتب على `ADMIN_EMAIL` الثابت فقط (index.ts:2074-2135). حارس «sole-admin guard» يمنع تعطيل/حذف حساب `ADMIN_EMAIL` (index.ts:641-645). حقل `role` في auth.users يُعاد في قائمة المستخدمين (1669) لكنه غير مستعمل في أي قرار. |
| **الناقص** | لا مفهوم «مستخدم أدمن» إطلاقاً: بيانات اعتماد كل الأدمن هي سرّ دالة واحد مشترك؛ لا جدول أدمن ولا أدوار (owner/manager/viewer)؛ الـaudit log يسجّل `ADMIN_EMAIL` الثابت لكل فعل (لكل نداءات logAdminAction) فلا يوجد نفي مسؤولية لفرد؛ 2FA مصممة لحساب واحد فقط. |
| **الجهد** | **L** — يتطلب: نقل الهوية إلى auth.users (أو جدول `admin_users` + أدوار)، إعادة كتابة `authAdmin` لتقرأ role، تجميد منطق sole-admin guard، وتوسيع `admin_2fa` لعدة صفوف، وتعديل كل `logAdminAction(ADMIN_EMAIL, …)` (~30 موضعاً) لتمرير هوية المتصل من التوكن. |

### ب) بوابات دفع (Stripe/PayPal)
| | |
|---|---|
| **الموجود اليوم** | **لا يوجد أي نموذج دفع.** لا جدول فواتير/مدفوعات في أي migration (0001-0014: codes/gyms/coupons/drive_tokens/contact_messages/admin_audit_log/error_log/admin_2fa/expiry_notices). نظام القسائم (`coupons`) هو «مخزن قيمة» منطقي فقط: `days_14/days_30/days_365/days_custom/percent` مع redeem/release ذرّي بشرط `eq("used", false)` (index.ts:1440-1452) — يمنح اشتراكاً زمنياً ولا يمس مالاً. جدول `ledger` على العميل (`js/store.js:10`) هو **دفتر إيرادات النادي الزبون تجاه أعضائه**، وليس فوترة GymOS. |
| **الناقص** | جدول `payments`/`invoices` + webhooks موقّعة + ربط تلقائي الدفع→تمديد اشتراك (اليوم كل تمديد يدوي عبر `runUserOp`/PATCH subscription) + ضريبة/عملة. |
| **الجهد** | **L** — البنية التحتية جيدة (composer واحد لتمديد الاشتراك عبر `codeWindowPatch`/`subMeta` يجعل «الدفع ناجح → مدّد» نقطة إدراج واحدة)، لكن webhooks + idempotency + عهدة PCI ترفع الجهد. |

### ج) مركز إشعارات (prefs / WhatsApp)
| | |
|---|---|
| **الموجود اليوم** | إشعار واحد فقط: بريد انتهاء الاشتراك (gymos-expiry-cron كاملاً + dedup بجدول `expiry_notices` PK(email, sub_end) — `0014_expiry_notices.sql:14-19`). البنية نموذجية للتعميم: جدول dedup + audit لكل تشغيل + SMTP عبر nodemailer + تحقق سرّ كرون (cron/index.ts:346-353). `notifications` كمجموعة بيانات موجودة على العميل لكنها **محلية فقط ولا تُزامن** (`js/store.js:10` + استثناء صريح في cloudDump سطر 218 وmergeStates سطر 281-284). `contact_messages` = قناة واردة باتجاه واحد. |
| **الناقص** | جدول تفضيلات إشعار (قناة/تفعيل/توقيت)، إرسال قالب متعدد القنوات، WhatsApp Business API (قوالب معتمدة)، إشعارات push (جدول أجهزة + توكنات). |
| **الجهد** | **M** — الهيكل (جدول+dedup+كرون+audit) قابل للنسخ؛ القناة الجديدة = مزوّد + قوالب. تفضيلات المستخدم = migration + عمود/جدول + UI صغير. |

### د) تحليلات استخدام (usage analytics)
| | |
|---|---|
| **الموجود اليوم** | **صفر تتبع أحداث.** لا analytics/telemetry/منصة خارجية في js/* (فحص نمطي: `analytics|telemetry|gtag|posthog` = لا نتائج). أقرب موجودين: `admin_audit_log` (أفعال إدارية فقط، index.ts:585-599) و`error_log` (أخطاء ≥400 مع sanitize، index.ts:601-622) — سجلّان داخليان وليسا قياس استخدام. |
| **الناقص** | نموذج حدث (`events` table أو طرف ثالث)، تجهيز كود الـclient، خصوصية/موافقة (PWA + أندرويد). |
| **الجهد** | **M** — نقطة الإدراج موجزة: كل نداءات الـAPI تمر بـ`handler` واحد (index.ts:741) ويمكن إضافة جدول `events` (بالتصميم المحلي-أولاً لتفادي الحمل)، لكن التغطية الكاملة (client-side funnels) تحتاج عمل أكبر. |

### هـ) iOS / Native shell
| | |
|---|---|

### و) سلاسل نوادٍ متعددة (multi-gym chains)
| | |
|---|---|
| **الموجود اليوم** | نموذج البيانات أحادي النادٍ: كل بيانات نادٍ مفتاحها `(code, device_id)` (`0002_admin_controls.sql:12-31`). `ownedCodesFor` تجمع كل أكواد المالك (`gymos-api/index.ts:248-253`) — أي مالك إيميل واحد **قد** يملك عدة أكواد، و`/api/auth/mine` يختار **أحدث كود فقط** (`recent[0]`, index.ts:994-996) ويضيف الجهاز له. التفعيل الجديد ينسخ بيانات النادي القديم إلى المفتاح الجديد (gyms continuity، index.ts:872-898) — أي «انتقال» وليس «تعدد». |
| **الناقص** | مفهوم `chain_id`/`gym_group`، ربط أكواد تحت مظلّة مالك واحد مع تبديل سياق في الـUI، تجميع تقارير، فصل صلاحيات (أدمن السلسلة ≠ أدمن النادٍ). |
| **الجهد** | **L** — يتطلب migration للعلاقات + إعادة تفكير مفاتيح العرض (لوحة الأدمن تعرض لكل كود مستقلاً) + خيار تبديل نادٍ في app.html. النسخ في التفعيل (872-898) ستتحول لعمليات ربط. |

## 4) سجل مخاطر فقدان بيانات العملاء / Customer Data-Loss Risk Register

### أقوى 3 نقاط
1. **مصدر حقيقة واحد للحقول الحرجة:** الـcomposer (`index.ts:134-203`) يجعل الخادم غير قادر على نفي نفسه حول الاشتراك/الانتهاء/التعليق، مع عقد مكتوب (`docs/CONTRACT-activation-v1445.md` §2) واختبار عقد يمنع عودة الـcomposer المزدوج (`tests/activation-contract.test.mjs:191`).
2. **إقفال قاعدة البيانات حقيقي:** RLS مفعّل بصفر سياسات anon على كل الجداول (`0009_lockdown_rls_complete.sql:21-51`) — الأمان لا يعتمد على صحة العميل إطلاقاً، والوصول الحصري عبر service_role في الدوال.
3. **انضباط تشغيلي آلي:** كل عملية إدارية تتدقيق (`logAdminAction`، index.ts:585-599) + rate limiting موجه حسب الخطورة (30/د عام، 5/5د تحطيمي، 473-486) + قفل إصدار versionCode↔cache آلي بـrelease.mjs واختباره (139-142).

### أخطر 3 نقاط
1. **لا نسخة احتياطية لأي حساب عميل (auth.users)** — `GET /api/admin/backup` يغطي codes+gyms حصراً (index.ts:1201-1210)؛ فقدان المشروع = إعادة تسجيل كل العملاء يدوياً بلا سجل اشتراكاتهم.
2. **تسريب اعتماد بسجل التدقيق:** `expected_prefix` (4 محارف من كلمة سر الأدمن الحقيقية) و`raw_body_preview` (يحوي كلمة السر المُدخلة) يُخزَّنان نهائياً في `admin_audit_log` عند فشل الدخول (index.ts:1100-1112) — خارج تغطية `sanitizeForLogging`.
3. **فقدان صامت من وجهة نظر العميل:** checkins محلية بلا نسخ (`store.js:218، 281-284`) وصفوف per-device يتيمة عند إعادة تفعيل المزامنة (`index.ts:1064/1080` بلا دمج) — حالتان يصفهما العميل بـ«ضاع الكل» رغم سلامة الخادم.
